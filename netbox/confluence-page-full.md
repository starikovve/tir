<h2>РЕГЛАМЕНТ РАБОТЫ С СЕРВИСОМ NetBox</h2>
<p><em>Сетевой отдел · Внутренний документ · Версия 1.5</em></p>
<h2>1. Назначение</h2>
<p>NetBox является единым источником истины (source of truth) сетевой инфраструктуры компании. Все данные о VLAN, подсетях, префиксах и сетевом оборудовании вносятся исключительно через NetBox. Конфигурации сетевых устройств строятся на основе данных NetBox. Любые изменения в инфраструктуре сначала фиксируются в NetBox, затем применяются на оборудовании.</p>
<h2>2. VLAN-группы</h2>
<p>VLAN-группы используются для логического разделения VLAN по площадкам и по оборудованию, на котором терминируются сети. Каждая VLAN-группа привязывается к одной площадке или к одному такому устройству: это закрепляет область видимости VLAN и гарантирует уникальность ID внутри группы.</p>
<ul>
  <li>Создать VLAN-группу: меню IPAM → VLANs → VLAN Groups → кнопка + Add.</li>
  <li>Поле Name — название группы, отражающее отдел и площадку или оборудование, например: <code>vlan-group-sales-msk</code>, <code>vlan-group-it-spb</code>, <code>vlan-group-agg01</code>.</li>
  <li>Поле Slug — URL-идентификатор, формируется автоматически из имени (латиница, строчные буквы, дефисы).</li>
  <li>Поле Scope — привязка группы к объекту: регион, группа сайтов, сайт, локация, группа стоек, стойка, группа кластеров или кластер. Выбирается та площадка или то оборудование, к которому относится группа.</li>
  <li>Поле VLAN ID Ranges — список допустимых диапазонов VID внутри группы (например <code>100-199,300-399</code>; диапазоны не должны пересекаться). По умолчанию 1–4094. При необходимости сужается под нужды отдела.</li>
  <li>Внутри одной группы каждый VLAN ID и имя уникальны. VLAN из разных групп могут иметь совпадающие ID — это нормально и не является ошибкой.</li>
</ul>
<p><strong>Правило: одна VLAN-группа — это одна площадка или одно оборудование, на котором терминируются сети (например, ядро или агрегация). Отдел может иметь несколько VLAN-групп — по числу площадок. Не создавать «общую» группу для всей компании.</strong></p>
<h3>Примеры применения</h3>
<ol>
  <li>Отдел с двумя площадками. Отдел продаж работает в Москве и Санкт-Петербурге — создаются две группы: <code>vlan-group-sales-msk</code> и <code>vlan-group-sales-spb</code>. Scope каждой группы — свой сайт. VLAN с одинаковыми ID на разных площадках конфликта не вызывают.</li>
  <li>Оборудование-агрегатор для нескольких отделов. На одном физическом коммутаторе агрегации терминируются сети нескольких отделов — для этого устройства создаётся одна группа, например <code>vlan-group-agg01</code>. Все VLAN, терминируемые на нём, вносятся в эту группу, и уникальность VID проверяется ровно там, где она нужна.</li>
  <li>Площадка без чёткой принадлежности отделу. Для площадки, которая не закреплена за конкретным отделом (склад, удалённый офис, серверная), группа называется по имени площадки, например <code>vlan-group-ekb-warehouse</code>.</li>
</ol>
<h2>3. VLAN</h2>
<p>VLAN создаётся в меню IPAM → VLANs → VLANs → кнопка + Add (или через вкладку Bulk Create формы создания для массового ввода ID и диапазонов, например: <code>100,200-210</code>, с плейсхолдером <code>{vid}</code> в имени, например <code>VLAN-{vid}</code>).</p>
<ul>
  <li>Обязательные поля: ID (VID 1–4094), Name (имя как на конфигурации коммутатора), Status.</li>
  <li>Поле VLAN Group — группа, к которой относится VLAN. Назначается всегда. Прямая привязка VLAN к сайту в NetBox объявлена устаревшей (deprecated) и регламентом не используется.</li>
  <li>Поле Role — функциональная роль VLAN (Data, Voice, Management и т. п.), если применимо.</li>
  <li>Поле Tenant — арендатор, при необходимости.</li>
</ul>
<h2>4. Префиксы (подсети)</h2>
<p>Префикс создаётся в меню IPAM → Prefixes → Prefixes → кнопка + Add. К одному префиксу может быть привязан VLAN из любой группы — ограничений по группам нет. Это позволяет, например, привязать к префиксу отдела продаж VLAN из группы мониторинга.</p>
<ul>
  <li>Поле Prefix — сеть в CIDR-нотации, например <code>10.40.10.0/24</code>.</li>
  <li>Поле Status — операционный статус: Active, Reserved, Deprecated и др.</li>
  <li>Поле VRF — экземпляр VRF, если префикс находится в нём.</li>
  <li>Поле Role — функциональная роль префикса (согласуется с ролью привязанного VLAN).</li>
  <li>Поле VLAN — VLAN, которому принадлежит префикс. Выбирается из списка с учётом группы.</li>
  <li>Поле Scope — регион, группа сайтов, сайт или локация (с NetBox 4.2 заменило поле Site).</li>
  <li>Поле Is a pool — все адреса префикса (включая сетевой и широковещательный) считаются пригодными для назначения.</li>
  <li>Поле Mark utilized — принудительная отметка 100% утилизации.</li>
</ul>
<h2>5. Теги</h2>
<p>Теги создаются администратором в меню Customization → Tags → кнопка + Add (поля: Name, Slug, Color, Description, Weight, Object Types). После создания тег назначается объектам через поле Tags в формах создания и редактирования.</p>
<ul>
  <li>Префиксам назначаются теги, отражающие их назначение или зону ответственности.</li>
  <li>Оборудованию назначаются теги по сетям, за которые оно отвечает. Пример: оборудование мониторинга помечается тегом mon.</li>
  <li>Имена тегов — короткие, латиницей, строчными буквами: mon, core, dist, access.</li>
</ul>
<h2>6. Description и комментарии префиксов</h2>
<p>Каждый префикс обязан иметь заполненное поле Description с кратким назначением подсети. Номер тикета на изменение или выделение подсети указывается в поле Comments в формате: <code>Ticket: NET-1234</code>. Без номера тикета префикс считается незадокументированным и подлежит исправлению.</p>
<h2>7. Роли оборудования</h2>
<p>Роли устройств создаются в меню Devices → Device Roles → кнопка + Add (модель DCIM). Каждому устройству назначается ровно одна роль (роль задаётся у устройства, а не у типа оборудования). Базовый набор ролей:</p>
<ul>
  <li>core — ядро сети (core switches);</li>
  <li>dist — дистрибуционный уровень (distribution switches);</li>
  <li>access — уровень доступа (access switches).</li>
</ul>
<p>Роль назначается в поле Role при создании устройства (Devices → Devices → + Add, подробно — в разделе 8). Дополнительно устройству задаются теги по сетям, за которые оно отвечает.</p>
<h2>8. Добавление оборудования</h2>
<p>Устройство создаётся в меню Devices → Devices → кнопка + Add. Порядок действий:</p>
<ol>
  <li>Заполнить обязательные поля: Name, Device role (core / dist / access), Device type, Site, Status (обычно Active).</li>
  <li>Привязать к месту установки: Location, Rack, Rack face (Front/Rear) и Position (нижний занимаемый юнит). При необходимости — Tenant, Platform, Tags (зоны ответственности).</li>
  <li>Заполнить Description и указать номер тикета в Comments (<code>Ticket: NET-1234</code>) — так же, как для префиксов.</li>
  <li>Интерфейсы: создаются автоматически из шаблонов Device type или добавляются вручную на вкладке Interfaces устройства (+ Add Components → Interfaces).</li>
  <li>IP-адрес берётся из выделенного префикса: IPAM → IP Addresses → IP Addresses → + Add, либо на странице префикса вкладка IP Addresses / кнопка Add an IP Address (свободные адреса показываются в списке).</li>
  <li>В форме IP-адреса на вкладке Interface assignment выбрать Device и Interface. Можно сразу отметить «Make this the primary IP for the device/VM».</li>
  <li>Либо отредактировать устройство и выбрать Primary IPv4 / Primary IPv6. Выбрать можно только адрес, уже назначенный интерфейсу этого устройства.</li>
</ol>

<h3>Типы устройств (Device Types)</h3>
<p>Device type — шаблон модели оборудования: производитель, модель, высота и глубина, а также шаблоны компонентов (interface templates, console port / power port templates и др.). При создании устройства этого типа NetBox автоматически создаёт на нём реальные компоненты (интерфейсы, порты) по шаблонам. Изменения типа позже не применяются к уже созданным устройствам задним числом.</p>
<ul>
  <li>Сначала создаётся производитель: Devices → Manufacturers → + Add.</li>
  <li>Затем тип: Devices → Device Types → + Add. Поля: Manufacturer (manufacturer), Model (model), Slug (slug), Height (U) (u_height; 0 — не монтируется в стойку), Is full depth (is_full_depth), Airflow (airflow, например Front to rear). При необходимости: Part number, Default platform, Exclude from utilization, Weight.</li>
  <li>Шаблоны интерфейсов: на странице типа кнопка + Add Components → Interfaces. Поля: Name, Type, Management only, Description. Тип выбирается из списка NetBox, например SFP+ (10GE), QSFP+ (40GE).</li>
  <li>Шаблоны создаются пачкой по шаблону имени с диапазоном в квадратных скобках: <code>TenGigabitEthernet1/0/[1-24]</code> создаёт 24 шаблона.</li>
  <li>Готовые типы можно загрузить через Devices → Device Types → Import (YAML), взяв описание из библиотеки сообщества: <code>github.com/netbox-community/devicetype-library</code>.</li>
</ul>

<h2>9. Обязательные правила</h2>
<ol>
  <li>Любые изменения инфраструктуры — перенос оборудования, удаление сетей, расформирование и другие изменения — в первую очередь вносятся в NetBox. NetBox является источником истины, остальные системы синхронизируются с ним.</li>
  <li>Никаких изменений на оборудовании без предварительной записи в NetBox.</li>
  <li>VLAN без группы не создаются.</li>
  <li>Префикс без description и номера тикета в comments не принимается.</li>
  <li>У каждого устройства — ровно одна роль и теги зон ответственности.</li>
  <li>Теги и роли не удаляются при наличии привязанных объектов.</li>
</ol>

## Запасной вариант: список задач вместо опроса

Используйте, если приложение Survey and Vote Macros не установлено (иначе будет «Unknown macro»)
или нужно видеть, кто **не** ознакомился. Замените секцию «Подтверждение ознакомления»
(макрос `survey`) на этот блок:

```xml
<h2>Подтверждение ознакомления</h2>
<p>Отметьте свою задачу после прочтения регламента.</p>
<ac:task-list>
  <ac:task><ac:task-status>incomplete</ac:task-status>
    <ac:task-body><ac:link><ri:user ri:account-id="ACCOUNT_ID_1" /></ac:link> ознакомлен с регламентом NetBox v1.5</ac:task-body></ac:task>
  <ac:task><ac:task-status>incomplete</ac:task-status>
    <ac:task-body><ac:link><ri:user ri:account-id="ACCOUNT_ID_2" /></ac:link> ознакомлен с регламентом NetBox v1.5</ac:task-body></ac:task>
</ac:task-list>
```

`ACCOUNT_ID_*` замените на ID пользователей Confluence Cloud (в Server/Data Center вместо
`ri:account-id` используется `ri:userkey` или `ri:username`).
