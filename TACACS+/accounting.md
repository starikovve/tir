# Учёт и журналы

Куда какая запись попадает, решает NAS (он шлёт accounting-пакет) и демон (он выбирает файл). Авторизация команды и учёт команды — разные сообщения. Первое решает, можно ли выполнить. Второе фиксирует, что команду уже отправили на устройство.

## Куда пишет tac_plus-ng

В [`server/tac_plus-ng.cfg`](server/tac_plus-ng.cfg) три назначения:

| Директива | Путь | Что внутри |
| --- | --- | --- |
| `authentication log` | `/var/log/tac_plus-ng/authc/%Y/%m/%d.log` | Удачные и неудачные проверки пароля |
| `authorization log` | `/var/log/tac_plus-ng/authz/%Y/%m/%d.log` | Какой профиль выбран и какая команда разрешена или запрещена |
| `accounting log` | `/var/log/tac_plus-ng/acct/%Y/%m/%d.log` | То, что NAS прислал как accounting |

`%Y/%m/%d` разбирается как `strftime`: 28 октября 2026 года — это файл `…/acct/2026/10/28.log`. Каталоги `authc`, `authz`, `acct` создают до старта, иначе демон не откроет назначение. `umask = 0640` задаёт права новых файлов.

Классический tac_plus пишет учёт в один файл из директивы `accounting file` (в примере `/var/log/tac_plus/tac_plus.acct`) и, при `accounting syslog;`, ещё в syslog. Отдельных `authentication log` / `authorization log` у него нет: служебные сообщения идут в syslog (`logging`), учёт — в accounting file.

Формат строки accounting у tac_plus-ng — текст, поля разделены табуляцией. Сначала фиксированный набор, затем пары `атрибут=значение`, как их прислал NAS. Обязательное поле среди пар — `task_id`. Руководство перечисляет фиксированную часть так: время, адрес NAS, имя, порт, адрес NAC (клиента администратора), тип записи (`start` / `stop` / `update`).

Пример строки сессии (табуляция между полями; здесь она показана как визуальный разрыв):

```text
2026-10-28 14:01:02 +0000	192.0.2.21	alice	tty1	203.0.113.10	start	task_id=42	service=shell	priv-lvl=15
2026-10-28 14:18:44 +0000	192.0.2.21	alice	tty1	203.0.113.10	stop	task_id=42	service=shell	priv-lvl=15	elapsed_time=1062
```

Пример командного учёта. Имена атрибутов зависят от NOS. IOS часто шлёт `cmd` и несколько `cmd-arg`. Junos кладёт текст команды в свои атрибуты `interactive-commands`. Демон не переименовывает их в единую схему:

```text
2026-10-28 14:02:11 +0000	192.0.2.21	alice	tty1	203.0.113.10	stop	task_id=42	service=shell	priv-lvl=15	cmd=show	cmd-arg=running-config
2026-10-28 14:05:40 +0000	192.0.2.24	bob	ssh	203.0.113.20	stop	task_id=77	service=junos-exec	cmd=show interfaces terse
```

`elapsed_time` — длительность в секундах, её присылает NAS в записи `stop`. Если командный учёт на NAS не включён, в файле будут только start/stop сессии, и это не поломка демона.

Поля, которые руководство прямо называет возможными в хвосте строки: `service`, `start_time`, `port`, `elapsed_time`, `status`, `priv_level` / `priv-lvl`, `cmd`, `protocol`, `cmd-arg`, `task_id`, `timezone`. Неизвестный атрибут NAS тоже попадёт в хвост как `имя=значение`.

## Ротация

Дневной путь уже ротирует запись: в полночь демон открывает новый файл, вчерашний больше не держит. Старые дни можно сжимать, не боясь оборвать текущую запись:

```text
/var/log/tac_plus-ng/acct/*/*/*.log
/var/log/tac_plus-ng/authc/*/*/*.log
/var/log/tac_plus-ng/authz/*/*/*.log
{
    daily
    rotate 90
    missingok
    notifempty
    compress
    delaycompress
    su root adm
}
```

Если назначение переписать на один неменяющийся путь (`destination = /var/log/tac_plus-ng/acct.log`), файл демон держит открытым. Тогда в logrotate нужен `copytruncate`, либо сигнал, после которого процесс откроет файл заново. `SIGHUP` мастер-процессу tac_plus-ng — это не «переоткрыть логи», а перечитать конфигурацию и перезапустить работников: старые дочитывают текущие соединения и выходят. Для смены файла этого достаточно, для ежечасной ротации удобнее путь со `strftime` или `copytruncate`.

Классический `tac_plus.acct` тоже лучше резать через `copytruncate`: демон блокирует файл через `fcntl`, и переименование из-под него даёт запись в уже переименованный inode. Файл держите на локальной ФС, не на NFS: блокировка по NFS в руководстве Shrubbery прямо названа ненадёжной.

## Поиск

Табуляция — разделитель, пробелы внутри времени и аргументов команды не путают поля, если резать по `\t`.

```bash
# Все записи пользователя alice за день
awk -F '\t' '$3 == "alice"' /var/log/tac_plus-ng/acct/2026/10/28.log

# Только команды с конкретного NAS
awk -F '\t' '$2 == "192.0.2.21" && /cmd=/' /var/log/tac_plus-ng/acct/2026/10/28.log

# Неудачные логины — это журнал аутентификации, не accounting
grep -F 'alice' /var/log/tac_plus-ng/authc/2026/10/28.log
```

Если регулярное выражение в профиле «не видит» команду, смотрят `authz/%Y/%m/%d.log`: там строка в том виде, в каком NAS положил её в `cmd`. Под это и подгоняют `if (cmd =~ …)`, а не под то, как команда выглядит на экране оператора.

## Отладка сервера

Временно, внутри `id = tac_plus-ng` (или внутри одного `device` / `user`):

```text
debug = AUTHEN AUTHOR ACCT PACKET CMD REGEX
```

Имена — из руководства tac_plus-ng (раздел Trace Options): `AUTHEN` аутентификация, `AUTHOR` авторизация, `ACCT` учёт, `PACKET` дамп пакета, `CMD` поиск команды, `REGEX` как сравнивалась регулярка. `USERINPUT` добавляют только на минуту: в журнал попадает введённый пароль. Снимают флаг и перечитывают конфигурацию (`SIGHUP` мастеру или рестарт службы).

Синтаксис без запуска: `tac_plus-ng -P /etc/tac_plus-ng.cfg`. Ключ `-d` у бинарника существует, руководство советует предпочесть директиву `debug`.

У классического демона уровни — битовая маска того же происхождения (`-d`), отдельного журнала авторизации нет, смотрят syslog и `accounting file`.

Типичные расхождения, которые эти флаги сразу показывают:

| Симптом | Куда смотреть |
| --- | --- |
| Пакет есть, пользователя «нет» | Ключ не совпал: тело не разбирается. Сверьте `key` устройства и `device` по адресу источника, не по адресу назначения. |
| Пароль верный, оболочка не открывается | В `authz` нет `permit` на пустой `cmd` и `priv-lvl` (IOS/VRP) или нет `local-user-name` (Junos). |
| `show` запрещён, хотя регулярка есть | NAS прислал команду иначе (`show` vs `sho`, аргументы отдельно). Ориентир — сырой `cmd` в журнале авторизации. |
| Учёт пустой | На NAS не включён accounting, либо пакеты уходят с другого source и не попадают в `device`. |

## Отладка на Cisco IOS / IOS-XE

Включают на время диагностики и выключают. На загруженном маршрутизаторе `debug tacacs` заметно шумит.

```ios
terminal monitor
debug tacacs
debug tacacs events
debug aaa authentication
debug aaa authorization
debug aaa accounting
```

Точное имя пакетного отладочного режима зависит от поезда: `debug tacacs ?` покажет `packet` или `packets`, если образ его умеет. Не угадывают скрытый подрежим.

Что ожидать:

- `debug aaa authentication` — какой метод-лист выбран и ответил ли сервер FAIL или просто тишина (таймаут, тогда сработает `local`);
- `debug aaa authorization` — ушла ли команда и какой уровень; пустой ответ по exec означает, что сервер не вернул разрешение на оболочку;
- `debug aaa accounting` — ушёл ли start/stop. Если здесь запись есть, а файла на сервере нет, пакет не дошёл или пришёл с чужого адреса;
- `debug tacacs events` — открытие TCP, таймаут, смена сервера в группе.

Состояние серверов без отладки:

```ios
show tacacs
show aaa servers
undebug all
```

`show tacacs` показывает, открыт ли single-connection и не помечен ли сервер мёртвым. После `undebug all` снимают и `terminal monitor`, если сессия больше не нужна.

На Junos аналог по смыслу — трассировка системы (`set system tacplus-options` сам по себе журнал пакетов не включает) и файлы `authc`/`authz` на сервере: устройство либо прислало `service=junos-exec`, либо нет. На VRP смотрят `display hwtacacs-server template` и те же серверные журналы. На RouterOS TACACS+ отлаживать нечего: счётчики в `/radius monitor` относятся к RADIUS из [`devices/mikrotik-routeros.md`](devices/mikrotik-routeros.md).
