# MLAG в OcNOS (IP Infusion): режимы, сценарии отказа и автоматизация failover

## С нуля: что такое MLAG и зачем это нужно

**Зачем два коммутатора вместо одного.** Если сервер или соседний коммутатор подключён к одному
коммутатору, то этот коммутатор — единственная точка отказа. Сломался он, перезагрузился или его
выключили по ошибке — всё, что в него воткнуто, остаётся без связи. Второй коммутатор ставят, чтобы
отказ одного не останавливал работу.

**Что будет без MLAG.** Пусть сервер подключён только к первому коммутатору. Первый коммутатор умер —
весь трафик через его порты пропадает, пока его не починят. Можно подключить сервер к двум
коммутаторам двумя отдельными кабелями, но без договорённости между коммутаторами это две разные
связи: серверу придётся самому решать, какой из них пользоваться, а сети — разбираться с петлями.

**Как MLAG это решает.** Два коммутатора договариваются между собой и для подключённого устройства
притворяются одним коммутатором. Сервер подключается к обоим сразу и объединяет кабели в одну
«толстую» связь (это делает протокол LACP). Для сервера это один логический линк, хотя кабели идут
в два разных коммутатора. Если один коммутатор умирает, у сервера просто становится на один кабель
меньше, а связь продолжает работать через второй.

**Что значит active-standby.** В нашем варианте MLAG один коммутатор активный — через него идёт
трафик, второй — резервный (standby): он подключён, всё знает о состоянии первого и готов
мгновенно подхватить работу. Пока активный жив, резервный трафик не пропускает. Если активный
пропал, резервный становится активным.

Дальше — подробности, как это устроено в OcNOS, какие есть настройки и где подвохи.

## a) Обзор

- **MLAG в OcNOS** работает в режиме **active-standby**: две ноды образуют один логический LACP-партнёр
  для хоста или соседнего коммутатора; трафик форвардит активная нода, стейнбай держит member-порты в резерве.
- **MCEC-домен** (Multi-Chassis Ether Channel) — логический домен из двух нод (domain-system-number 1 и 2)
  с общим domain-address.
- **IDL (intra-domain link)** — линк для data-трафика между нодами.
- **IDP (intra-domain peer)** — healthcheck и синхронизация состояний: hello и info PDU,
  синхронизация MAC/ARP/FDB.
- IDP может идти через **VRF management** как обычный L3-интерфейс в bridge-VLAN с IP на каждой ноде:
  `intra-domain-peer <peer-ip> source-address <local-ip> vrf management`.

```text
            Хост / соседний коммутатор (LACP)
                 |                 |
           member-порт        member-порт
                 |                 |
          +------+------+   +------+------+
          |  Node-1     |===|  Node-2     |   === IDL (data)
          |  ACTIVE     |---|  STANDBY    |   --- IDP (hello/info, MAC/ARP/FDB sync)
          +------+------+   +------+------+
                 |                 |
             L3 uplink         L3 uplink
```

## b) Варианты настройки MLAG и переключения

| Опция | Что делает | Плюсы | Минусы |
|---|---|---|---|
| `strict-active-standby` **enabled** (дефолт с OcNOS 6.5.2) | При падении adjacency стейнбай молчит. При reload мастера через CLI OcNOS стейнбай берёт роль; при power-cycle / Linux-reboot / crash мастера стейнбай **не** берёт роль | Защита от split-brain | Слепое пятно на внезапную смерть ноды: 100% потеря трафика до восстановления мастера |
| `strict-active-standby` **disabled** | Стейнбай активируется при любом падении adjacency, включая смерть ноды | Переживает смерть ноды | При падении IDL (а не ноды) обе ноды станут active: split-brain, dual-active, MAC-флэппинг, дубли ARP. Ожидаемый network disruption |
| **dynamic MLAG** | Мастер выбирается эвристикой (число живых аплинков, uptime), не ждёт ручной приоритет | Роль получает «здоровая» нода | Менее предсказуемо, сложнее разбор инцидентов |
| **fast failover** | Укороченные таймеры heartbeat, переключение за доли секунды | Минимальный простой | Выше риск ложных переключений при кратких потерях hello |
| **Проверка консистентности VLAN/LAG** | Ругается при рассинхроне VLAN/LAG между нодами | Ловит ошибки конфигурации до аварии | Предупреждения нужно мониторить |
| `switchover type revertive <N>` (дефолт 10 с) | После восстановления изначально активная нода забирает роль обратно | Предсказуемый мастер | Лишнее переключение (микропрерывание) при возврате |
| `switchover type non-revertive` | Роль обратно не отдаётся | Нет второго переключения | Мастер «плавает»; вернуть роль — reload на активном |
| `domain-priority <1-65535>` (дефолт 32768) | Кто выше — тот живёт при сплит-брейне | Детерминированный исход split-brain | Нужно документировать и держать согласованным |
| `domain-hello-timeout long\|short` | Таймаут hello в домене | short — быстрее детект; long — устойчивее к потерям | short повышает риск ложного падения adjacency |
| `mcec domain configuration` | Режим домена: `domain-address`, `domain-system-number`, `intra-domain-peer`, `intra-domain-link` | Базовая настройка домена | Ошибка в любом параметре — домен не сойдётся |
| `mode active-standby` / `active-active` на `interface mlagN` | Режим MLAG-интерфейса | active-standby — основной поддерживаемый | active-active — **проверьте на вашей версии OcNOS** (в SP-справочнике только active-standby) |

Замечания по синтаксису:
- По справочнику `switchover type` задаётся на `interface mlagN`, диапазон указан `<1-255>` (не `<1-3600>`), дефолт 10 с — **проверьте на вашей версии OcNOS**.
- `strict-active-standby`, dynamic MLAG, fast failover, проверка консистентности и форс-дешутинг в SP-справочнике не найдены — точное имя команды и режим ввода (например, `mcec strict-active-standby` в config или `strict-active-standby` в `mcec domain`) **проверьте на вашей версии OcNOS** (6.5.2+).

## c) Сценарий: только IDL, активная нода умерла

1. **Reload мастера через CLI OcNOS** — стейнбай штатно встаёт в active, переключение чистое.
2. **Power-cycle / Linux-консоль / APC / crash** — при strict enabled стейнбай остаётся стейнбаем, 100% потеря трафика.
   - Ручной выход: на стейнбае `mcec strict-active-standby disable` — он активируется, но домен перестаёт быть MLAG в строгом смысле: два форвардера с общим MAC, LACP на хосте видит member-порты на обоих, ECMP идёт криво.
   - Uplink'и мёртвого мастера лучше вручную заглушить (`shutdown`), если до них есть доступ (консоль/OOB или соседний коммутатор).
3. **Восстановление:** поднять мастер в OcNOS → дождаться adjacency и `IN_SYNC` в `show mlag detail` → вернуть strict (`no mcec strict-active-standby`) → при revertive исходный мастер заберёт роль сам по таймеру, при non-revertive — reload на текущем активном.
4. **L3-линки** (uplink'и), которые гасили вручную при аварии, поднимать **после** того, как стейнбай снова ушёл в standby — иначе микрофлэп и дубли.

## d) Автоматизация переключения (внешний мониторинг)

- Zabbix / cron / маленький Linux-бокс пингует management-IP мастера и параллельно по SSH читает `show mcec` на стейнбае.
- **Условие failover:** мастер не отвечает N секунд **и** adjacency down — это смерть ноды, а не падение линка.
- **Действие:** SSH на стейнбай, `mcec strict-active-standby disable`.
- **Возврат:** мастер ожил + adjacency up → ждать `RECOVERY_WAIT` (60 с) → `no mcec strict-active-standby` → reload на активном (при revertive).
- **Ключевой подвох:** не спутать смерть мастера с падением IDP. Если упал только IDP, а мастер жив по management — переключать нельзя. Если management и IDP идут через одну сеть, пропажа mgmt-пинга может быть проблемой этой сети, а не ноды — получите split-brain.
- **Два IDP-линка** дают redundancy на уровне каналов и снижают вероятность ложного срабатывания.

## e) Процесс дешутинга (unshutting)

- После восстановления IPL (IDL/IDP) нода не поднимает MLAG-порты сразу: ждёт схождения FDB/ARP/LACP-стейтов с мастером.
- Затем порты поднимаются с задержкой — против повторного флэпа.
- Есть форс-команда для немедленного подъёма, если руками уверены в отсутствии рассинхрона; её имя **проверьте на вашей версии OcNOS**.

## f) Обслуживание MLAG

- Плановые reload'ы — только через CLI OcNOS (не Linux/APC); порядок — сначала стейнбай, потом мастер.
- Не трогать топологию во время upgrade.
- Перед и после работ проверять `show mlag detail` (`Mlag Sync IN_SYNC`) и `show mcec statistics` (счётчики RX hello растут).
- Бэкап конфигураций — через Oxidized.
- VLAN-консистентность сверять с NetBox как source of truth.
- Мониторить IDP-линки отдельно от data-сети.
- Документировать `domain-priority` и `domain-hello-timeout` в репозитории.

## Скрипт `mlag-failover.py`

Внешний монитор: пингует мастер, читает `show mcec` на стейнбае через Netmiko (`device_type="ipinfusion_ocnos"`).

- **Failover:** мастер не пингуется **и** adjacency `down` `FAIL_THRESHOLD` раз подряд → `disable_strict` (`mcec strict-active-standby disable`).
- **Recovery:** в режиме failover, мастер жив и adjacency `up` → ждёт `RECOVERY_WAIT`, перепроверяет → `enable_strict` (`no mcec strict-active-standby` в config mode) → если стейнбай `active`, `revert_role` (reload).

Настройка — переменные окружения (в скрипте только заглушки):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MASTER_MGMT_IP` | `192.0.2.1` | management-IP мастера |
| `STANDBY_MGMT_IP` | `192.0.2.2` | management-IP стейнбая |
| `OCNOS_USER` / `OCNOS_PASSWORD` | `CHANGE_ME` | SSH-учётка |
| `OCNOS_SSH_PORT` | `22` | SSH-порт |
| `FAIL_THRESHOLD` | `3` | подряд неуспешных проверок |
| `CHECK_INTERVAL` | `10` | интервал проверок, с |
| `RECOVERY_WAIT` | `60` | ожидание перед возвратом strict, с |

```bash
pip install netmiko
export MASTER_MGMT_IP=192.0.2.1 STANDBY_MGMT_IP=192.0.2.2 OCNOS_USER=... OCNOS_PASSWORD=...
python3 mlag-failover.py --dry-run   # только логирует действия
python3 mlag-failover.py --once      # одна проверка
python3 mlag-failover.py             # непрерывный мониторинг
```

> Формат вывода `show mcec` и синтаксис `mcec strict-active-standby` зависят от версии OcNOS —
> проверьте регулярные выражения и команды на стенде до боевого запуска.
